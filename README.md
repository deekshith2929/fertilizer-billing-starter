# Agri Dealer Hub

Stack: Java 25, Spring Boot, React/Vite, PostgreSQL. Billing is calculated in memory and stays runtime-only unless the operator explicitly selects a customer and saves the bill to that customer's account. Includes dealer-specific product catalogs and GST-inclusive prices, dynamic rows, bill-only custom products that are not saved to the catalogue, editable per-bill price, bag/weight calculation, GST calculation, preview and browser print/PDF. Supplier ledgers track opening balances, purchases, and payments without affecting stock.

For a product that is not in the catalogue, choose **Other / enter manually…** in a bill row. Enter the product name, bag weight, GST rate and price; HSN code is optional. These details are used only for the current calculation and are not written to the product catalogue or database.

## Requirements
JDK 25, Maven 3.9+, Node.js 20+, PostgreSQL.

## Database
Create `fertilizer_db`, then run `database/schema.sql`. Set `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` if needed. Defaults: `jdbc:postgresql://localhost:5432/fertilizer_db`, `fertilizer_app`, `change_me`.

Clients can submit location data with `POST /api/location-captures` using `latitude`, `longitude`, `accuracyMeters`, and ISO-8601 `capturedAt`. Each submission is stored in `location_captures` without user or dealer identifiers; the complete JSON payload is also retained in its `comments` column. Flyway migrations V12  create the table without user/dealer identifiers.

## Run
Terminal 1: `cd backend && mvn spring-boot:run`
Terminal 2: `cd frontend && npm install && npm run dev`
Open http://localhost:5173. The database is seeded with a demo account: `admin` / `admin123`. Login checks the active user, password hash, role, and dealer against PostgreSQL. New users must be stored in `app_users` with a PBKDF2-SHA256 password hash and linked to their role in `user_roles`.

Permissions are assigned to roles through the database `permissions` and `role_permissions` tables. Flyway migration V10 seeds the default access matrix and V11 makes ADMIN accounts global (unassigned to a dealer); `database/schema.sql` seeds the same defaults for fresh installs. The frontend uses the permissions returned at login to display modules, and backend APIs re-read the current database assignments when authorizing each request. SQL changes to `role_permissions` take effect immediately on APIs; users should sign in again to refresh the navigation they see.

The default `ADMIN` role has no dealer assignment and sees only the Admin module, where administrators can create dealers, create users assigned to a dealer, create other unassigned ADMIN accounts, update user details/passwords, and deactivate accounts. A `DEALER` sees the working modules plus Admin for managing employee accounts within their own dealership; an `EMPLOYEE` sees the working modules but not Admin. Dealer user managers can only create, update, reset passwords for, and deactivate employee accounts in their dealership. Removing a user deactivates the account and retains its records. Dealer creation accepts optional AGL and PL numbers; fertilizer and pesticide stock reports use the matching dealer number in their header and leave it blank when it has not been provided. Passwords are hashed by the backend; the UI never stores password hashes.

Users with the `DEALER` or `ADMIN` role can open **Products** to create, edit, restore, and deactivate dealer-specific products, and to insert or update default prices. Dealer users are restricted to their own dealer; admins can select a dealer. Deletion deactivates the product and price instead of removing the database record. Flyway migration V3 gives existing products with dealer prices a dealer-owned catalog row, cloning products when they were priced for multiple dealers.

Dealers and admins can open **Stock Report** to prepare fertilizer and pesticide reports for a date range. Product categories are managed in the product form; existing products are categorized as Fertilizer by Flyway migration V4. Report rows and their opening balances, receipts, and sales are runtime-only and are not saved. The most recent report's dates and rows are kept in the current browser session for quick reuse. Choose **Yes** for Authorized Stamp Required and upload JPG, PNG, or WebP images: the stamp and signature may be selected together, with the signature printed below the stamp, or select the combined stamp-and-signature image by itself. The selected image(s) are included in the PDF and are not stored. Print / Save PDF opens the browser print dialog.

Dealers and admins can open **Company / Dealer Ledger** to manage supplier accounts and enter an opening payable/advance, purchase invoice, or payment with a date, reference, and notes. Ledger entries can be corrected in place; every actual correction records the previous and new values, editor, and timestamp, and the running balance is recalculated from the corrected entry. The edit history is available from each entry. The ledger supports date-filtered statements and printing. These records do not update stock. Flyway migration V6 creates the supplier and ledger tables, and V7 adds edit history; `database/schema.sql` includes the same tables for fresh installations. Admins can select an active dealer.

The ledger's optional JPG, PNG, WebP, BMP, or PDF reader uses browser-side OCR to prefill transaction fields. The selected file is processed only in the browser, is limited to 10 MB, and PDFs are limited to the first five pages; the file is not sent to or stored by the backend. Tesseract.js downloads its OCR worker and English language data from jsDelivr when needed; only those engine assets are fetched, not the selected document. Review extracted values before saving because OCR can be inaccurate. Only the confirmed ledger fields are persisted.

The **Farmer / Customer Ledger** stores dealer-scoped customer accounts, manually entered opening balances/payments/adjustments, and customer bills explicitly saved from Billing. Saved invoices have a header and separate item rows that snapshot dealer/customer/product details, HSN, quantities, prices, GST, and totals; custom bill products are saved only as historical invoice-line details, never added to the product catalogue. Credit invoices increase the amount due. Cash invoices are recorded as a bill plus a matching settlement, so they remain in history without increasing the balance. Invoice lines can be repriced, have quantities corrected, or be removed for returned products; every edit requires a reason, preserves before/after line and total snapshots with the editor and time, and posts any invoice-total difference to the customer ledger. Flyway migrations V8 and V9 create the customer ledger and invoice edit history; `database/schema.sql` includes both for fresh installations.

Billing and stock report product fields support searching by typing and keyboard selection with the arrow keys and Enter. Billing remembers the last bill type and customer state code for the browser session, bill rows can be duplicated, and Ctrl+Backspace removes the focused selected row. Stock reports provide a Today shortcut, reuse of the previous report dates, and copying the previous report's rows.

## Netlify deployment
The frontend uses `http://localhost:8080/api` in development and defaults to `https://fertilizer-billing-starter.onrender.com/api` in production. In Netlify, set the `VITE_API_BASE_URL` environment variable to `https://fertilizer-billing-starter.onrender.com/api`, then trigger a new deploy; Vite embeds this value at build time. The backend must also allow the exact Netlify site origin through CORS.

For the Render backend, set `FRONTEND_ORIGIN=https://fertilizerdealersinventory.netlify.app`, `SESSION_COOKIE_SAME_SITE=None`, and `SESSION_COOKIE_SECURE=true`, then redeploy the backend. The origin must exactly match the browser address, with no trailing slash. Local development defaults remain localhost and do not require these variables.

## Important
This is a development starter, not production-ready. The demo account is seeded with a known development password; replace or disable it before deployment. Admin sessions use an HTTP-only server session cookie; serve over HTTPS and configure production CORS origins before network exposure. Other billing/product endpoints still need authenticated dealer scoping before deployment. Demo product prices/dealer data are illustrative. Tax/place-of-supply logic is simplified and must be reviewed before real use. Generated bills remain runtime-only unless explicitly saved to a customer account.
